Step 1 of 200 · Modern C++

Install a modern C++ compiler

Set up a compiler that supports modern C++, prove that the complete compile–run loop works, and learn exactly what the compiler is doing for you.

Definition of done: you can compile a C++20 program from a terminal, run it, identify your compiler and version, and explain the difference between source code and the executable it produces.

What you are installing—and why

C++ source files are plain text. Your computer cannot execute them directly. A compiler parses that text, checks the language rules, translates it to machine code, and produces object files. A linker then joins those object files with the C++ standard library into an executable.

For this roadmap, use a compiler with solid C++20 support:

  • Clang is the natural choice on macOS and an excellent choice on Linux.
  • GCC is the most common choice on Linux.
  • MSVC is the standard Windows toolchain and integrates with Visual Studio.
Why C++20? It gives us a modern baseline—structured bindings, concepts, ranges, improved concurrency tools and coroutine language support—without depending on brand-new compiler behavior.

Install the compiler

macOS

Install Apple’s Command Line Tools. This supplies clang++, the system headers, linker and debugger.

xcode-select --install

Complete the installer window, open a new terminal, then verify:

clang++ --version
xcode-select -p

Ubuntu or Debian Linux

sudo apt update
sudo apt install build-essential gdb
g++ --version

build-essential installs GCC, the C++ compiler, the linker and basic build tools. gdb is the debugger we will need later.

Fedora Linux

sudo dnf group install "Development Tools"
sudo dnf install gcc-c++ gdb
g++ --version

Windows

  1. Download Visual Studio Community or Build Tools for Visual Studio.
  2. Select Desktop development with C++.
  3. Keep MSVC, the Windows SDK and C++ CMake tools selected.
  4. Open Developer PowerShell for VS and run cl.

A version banner confirms that MSVC is available. Use the Developer PowerShell because it configures the environment variables that cl.exe needs.

Compile your first program

Create hello.cpp with this code:

#include <iostream>

int main() {
    std::cout << "Compiler ready!\n";
    return 0;
}

On macOS with Clang:

clang++ -std=c++20 -Wall -Wextra -Wpedantic hello.cpp -o hello
./hello

On Linux with GCC:

g++ -std=c++20 -Wall -Wextra -Wpedantic hello.cpp -o hello
./hello

On Windows in Developer PowerShell:

cl /std:c++20 /W4 /EHsc hello.cpp
.\hello.exe

You should see Compiler ready!.

Understand the command

  • -std=c++20 selects the language version.
  • -Wall -Wextra -Wpedantic enables useful warnings. Warnings often reveal bugs before the program runs.
  • hello.cpp is the translation unit to compile.
  • -o hello names the executable.
  • MSVC’s equivalents are /std:c++20, /W4 and /EHsc.
Good habit: treat warnings as work to resolve, not background noise. Clean warning output is part of a healthy C++ project.

Prove errors are useful

Temporarily remove the semicolon after the std::cout statement and compile again. Read the first diagnostic carefully. Compilers may emit several follow-on errors, but the first one usually points closest to the cause. Restore the semicolon and recompile.

Common failure: “command not found” means the tool is not installed or is not on your shell’s PATH. Reopen the terminal after installation. On Windows, use the Developer PowerShell.

Completion checklist

  • The compiler version command works.
  • hello.cpp compiles with C++20 enabled.
  • The executable prints the expected output.
  • You can explain source file → compiler → object code → linker → executable.
  • You intentionally triggered, read and fixed one compiler diagnostic.

Step 2 of 200 · Modern C++

Set up VS Code or CLion

Turn a text editor into a reliable C++ workspace with completion, diagnostics, formatting, building and debugging—without hiding how the toolchain works.

Definition of done: your editor opens the project folder, understands C++ symbols, builds with warnings enabled, stops at a breakpoint, lets you inspect a variable and uses a consistent formatter.

Choose one editor

VS Code is lightweight and explicit: you assemble the extensions and build configuration. It is a good choice if you want to understand every layer. CLion is a full C++ IDE: project indexing, CMake and debugging work together with less setup. Both are professional tools; choose one and keep moving.

Path A: VS Code

1. Install the required extensions

  • C/C++ by Microsoft for IntelliSense and debugging.
  • CMake Tools by Microsoft—we will use it fully in Step 3.
  • CodeLLDB on macOS/Linux if you prefer LLDB debugging. On Windows, the Microsoft extension handles MSVC debugging.

Avoid installing several competing C++ language-server extensions at once. Duplicate analyzers can produce conflicting diagnostics and waste CPU.

2. Open a folder, not just a file

mkdir editor-check
cd editor-check
code .

Opening the folder gives VS Code a project boundary for settings, tasks and debugging. Create main.cpp:

#include <iostream>
#include <string>
#include <utility>

int main() {
    const std::string service_name = "roadmap-api";
    const int port = 8080;
    std::cout << service_name << " listens on " << port << '\n';
}

3. Configure a build task

Create .vscode/tasks.json. Use clang++ on macOS or g++ on Linux.

{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "build current project",
      "type": "shell",
      "command": "clang++",
      "args": [
        "-std=c++20", "-Wall", "-Wextra", "-Wpedantic",
        "-g", "${workspaceFolder}/main.cpp",
        "-o", "${workspaceFolder}/app"
      ],
      "group": { "kind": "build", "isDefault": true },
      "problemMatcher": ["$gcc"]
    }
  ]
}

Run Terminal → Run Build Task. The -g flag includes debug information so a debugger can map machine instructions back to source lines.

4. Configure debugging

Create .vscode/launch.json for LLDB:

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug app",
      "type": "lldb",
      "request": "launch",
      "program": "${workspaceFolder}/app",
      "cwd": "${workspaceFolder}",
      "preLaunchTask": "build current project"
    }
  ]
}

Set a breakpoint on the std::cout line and start debugging. Confirm the program pauses and that you can inspect service_name and port.

Windows/MSVC: Step 3 moves the project to CMake, which lets CMake Tools select MSVC cleanly. For this step, use the “C++: cl.exe build and debug active file” configuration generated by VS Code.

5. Add formatting

Create .clang-format:

BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
SortIncludes: CaseSensitive

Enable Format on Save. The file makes formatting deterministic across machines and editors.

Path B: CLion

  1. Install CLion and open the project folder.
  2. Under Settings → Build, Execution, Deployment → Toolchains, confirm that the C++ compiler, debugger and CMake entries are valid.
  3. Create the CMakeLists.txt from Step 3 below, or let CLion create a C++ executable project.
  4. Wait for indexing to finish. Red code during initial indexing is not necessarily a compiler problem.
  5. Choose the executable run configuration, set a breakpoint, then choose Debug.
  6. Inspect service_name and port in the variables pane.

CLion uses the project’s CMake model instead of inventing a separate build definition. The IDE and terminal therefore build the same targets.

Understand the layers

  • The editor changes text.
  • The language service indexes code and offers completion.
  • The compiler decides whether the program is valid.
  • The build system decides which commands to run.
  • The debugger controls a running executable and inspects its state.

Why this distinction matters: an editor warning is not always a compiler error. If red squiggles disagree with a successful terminal build, the editor’s project configuration is probably stale or incomplete.

Completion checklist

  • The editor opens the entire project folder.
  • Go-to-definition and completion work for standard-library symbols.
  • The project builds with C++20 and warning flags.
  • A breakpoint pauses the program.
  • You can inspect local variables during the pause.
  • Saving applies the shared formatting rules.

Step 3 of 200 · Modern C++

Install and use CMake

Replace one-off compiler commands with a reproducible build definition that works from the terminal, inside an IDE and later in continuous integration.

Definition of done: CMake configures a separate build directory, builds a named executable target with C++20 and warnings, and the executable runs successfully.

Why a build system exists

A real backend will have dozens of source files, libraries, tests and third-party dependencies. Typing one enormous compiler command is fragile. CMake describes targets and their requirements, then generates the concrete build files for Ninja, Make, Visual Studio or Xcode.

CMake has two stages:

  1. Configure/generate: read CMakeLists.txt, detect the toolchain and produce a build tree.
  2. Build: invoke the generated native build system to compile only what changed and link the targets.

Install CMake

macOS with Homebrew

brew install cmake ninja
cmake --version
ninja --version

Ubuntu or Debian

sudo apt update
sudo apt install cmake ninja-build
cmake --version

Fedora

sudo dnf install cmake ninja-build
cmake --version

Windows

Install CMake from the Visual Studio Installer’s C++ workload or from cmake.org. Allow the installer to add CMake to PATH. Open a fresh terminal and run cmake --version.

Version target: use CMake 3.20 or newer for this roadmap. The project declares 3.20 as its minimum so its commands have predictable behavior.

Create a minimal CMake project

Create this structure:

cmake-check/
├── CMakeLists.txt
└── src/
    └── main.cpp

src/main.cpp:

#include <iostream>

int main() {
    std::cout << "Built by CMake\n";
}

CMakeLists.txt:

cmake_minimum_required(VERSION 3.20)

project(cpp_backend_roadmap
    VERSION 0.1.0
    LANGUAGES CXX
)

add_executable(roadmap_app
    src/main.cpp
)

target_compile_features(roadmap_app PRIVATE cxx_std_20)

if(MSVC)
    target_compile_options(roadmap_app PRIVATE /W4 /permissive-)
else()
    target_compile_options(roadmap_app PRIVATE -Wall -Wextra -Wpedantic)
endif()

Read the build definition line by line

  • cmake_minimum_required defines the oldest CMake behavior the project accepts.
  • project names the project, gives it a version and enables only C++.
  • add_executable creates a target named roadmap_app from its source files.
  • target_compile_features requests C++20 for this target.
  • The compiler check assigns comparable warning levels for MSVC and Clang/GCC.
  • PRIVATE means this requirement belongs to the target and does not propagate to targets that consume it.
Why target-based CMake? Modern CMake models each executable or library as a target with its own sources, include paths, features and dependencies. This scales far better than global flags and directory-wide settings.

Configure, build and run

From the project root:

cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/roadmap_app

On Windows the executable may be build\roadmap_app.exe. With a multi-configuration Visual Studio generator, use:

cmake -S . -B build
cmake --build build --config Debug
.\build\Debug\roadmap_app.exe
  • -S . selects the current source directory.
  • -B build keeps generated files in build/.
  • -G Ninja chooses Ninja explicitly. Omit it to use the platform default.
  • cmake --build is generator-independent; it works with Ninja, Make or MSBuild.

Keep generated files out of source control

Add this to .gitignore:

/build/

The build directory is disposable. If configuration becomes confused, remove that specific build/ directory and configure again. Never edit generated files inside it.

Common mistake: running CMake without -B build creates generated files beside your source. An out-of-source build keeps the repository clean and makes Debug and Release build trees easy to separate.

Completion checklist

  • cmake --version works.
  • The source tree contains only authored files; generated output is in build/.
  • Configure and build complete without warnings.
  • The executable prints Built by CMake.
  • You can explain configure vs build and source tree vs build tree.
  • /build/ is ignored by Git.

Step 4 of 200 · Modern C++

Install and configure Git

Set up version control, learn the working-tree → staging-area → commit flow, and make a small history you can inspect and recover from.

Definition of done: Git is installed, your author identity is configured, line endings are sensible for your OS, and you can create, inspect and restore a local commit safely.

What Git tracks

Git stores snapshots of a project. Your working tree contains current files. The staging area is the exact proposed contents of the next snapshot. A commit stores that snapshot with its parent, author, time and message.

Why staging exists: it lets you build one focused commit from selected changes even when the working tree contains unrelated experiments.

Install Git

macOS

xcode-select --install
git --version

If you installed the compiler in Step 1, Git is likely already present. Homebrew’s newer release is also available with brew install git.

Ubuntu or Debian

sudo apt update
sudo apt install git
git --version

Fedora

sudo dnf install git
git --version

Windows

Install Git for Windows from git-scm.com. The default choices are suitable. Enable Git from the command line, choose your preferred editor, and keep the recommended Windows/Unix line-ending conversion. Then open a new terminal and run git --version.

Configure your identity and defaults

Use the name and email you want attached to future commits:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"

Inspect the result and where each setting came from:

git config --global --list
git config --list --show-origin

If you use CLion, omit the core.editor line or choose another terminal editor.

Line-ending policy

Use one of these global defaults:

# macOS or Linux
git config --global core.autocrlf input

# Windows
git config --global core.autocrlf true

Later, a repository-level .gitattributes file will define the canonical policy for the whole team. This global setting reduces accidental line-ending-only diffs meanwhile.

Practice the complete local workflow

mkdir git-practice
cd git-practice
git init
printf "# Git Practice\n" > README.md
git status
git add README.md
git diff --staged
git commit -m "Add project readme"
git log --oneline --decorate

On Windows PowerShell, replace the printf line with:

Set-Content -Path README.md -Value "# Git Practice"

Now edit the file and observe each view:

git status
git diff
git add README.md
git diff --staged
  • git diff shows unstaged differences: working tree versus staging area.
  • git diff --staged shows what the next commit would contain: staging area versus current commit.
  • git status is the safe first command whenever you are uncertain.

Learn one safe undo operation

Remove the modified file from the staging area without discarding its content:

git restore --staged README.md
git status

This moves only the index back to the committed version; your edits remain in the working tree. Do not reach for reset --hard while learning—it can permanently discard uncommitted work.

Create a C++-appropriate ignore file

# Build directories
/build/
/cmake-build-*/

# Compiled artifacts
*.o
*.obj
*.exe
*.out

# Editor and OS noise
.DS_Store
.vscode/*.log
.idea/

Do not ignore source code, CMakeLists.txt or a dependency lock file. Ignore generated artifacts because they can be reproduced from committed source.

Common mistake: adding secrets and then putting their filename in .gitignore. Ignore rules do not remove a file from existing commit history. Never commit credentials in the first place.

Completion checklist

  • git --version works.
  • Name, email and default branch are configured.
  • You can explain working tree, staging area and commit.
  • You created and inspected a commit.
  • You used git restore --staged without losing edits.
  • You understand why generated C++ build output is ignored.

Build the long-lived project workspace that will hold every experiment, exercise and backend service in this course, then publish its clean initial history.

Definition of done: a structured CMake project builds locally, repository rules are committed, the remote GitHub repository contains the same main commit, and no generated files or secrets are tracked.

Choose a structure that can grow

Create one repository with small applications and reusable code separated from generated output:

cpp-backend-roadmap/
├── CMakeLists.txt
├── README.md
├── .clang-format
├── .gitattributes
├── .gitignore

│   └── hello/

Create the files

mkdir -p cpp-backend-roadmap/apps/hello cpp-backend-roadmap/include \

New-Item -ItemType Directory -Force cpp-backend-roadmap/apps/hello,

/cmake-build-*/

compile_commands.json

Build before committing

Create a clean initial history

git add CMakeLists.txt README.md .clang-format .gitattributes .gitignore apps
git diff --staged
git commit -m "Initialize C++ backend roadmap"

Publish to GitHub

With GitHub CLI

Step 6 of 200 · Modern C++

Understand compilation vs linking

Take a two-file program through preprocessing, compilation, object generation and linking so compiler errors and linker errors stop looking like the same problem.

Definition of done: you can compile source files separately, inspect their object files, link them into one executable, and deliberately produce and diagnose both a compiler error and a linker error.

The build pipeline

  1. Preprocessing expands #include and macros.
  2. Compilation parses one translation unit, type-checks it and emits assembly or object code.
  3. Assembly turns assembly into machine instructions inside an object file.
  4. Linking resolves references between object files and libraries and produces the executable.

A translation unit is one source file after preprocessing. Each .cpp file is compiled independently; the linker is the first stage that sees the program as a whole.

Build a two-file program

Create math.cpp:

int add(int left, int right) {
    return left + right;
}

Create main.cpp:

#include <iostream>

int add(int left, int right);  // declaration

int main() {
    std::cout << add(20, 22) << '\n';
}

Compile without linking by using -c:

clang++ -std=c++20 -Wall -Wextra -Wpedantic -c main.cpp -o main.o
clang++ -std=c++20 -Wall -Wextra -Wpedantic -c math.cpp -o math.o
clang++ main.o math.o -o app
./app

Use g++ instead of clang++ on GCC. MSVC equivalents are cl /c main.cpp math.cpp followed by link main.obj math.obj /OUT:app.exe. The result should print 42.

Inspect the intermediate state

clang++ -std=c++20 -E main.cpp > main.ii
nm -C main.o | grep add
nm -C math.o | grep add

The preprocessed file is large because it contains expanded headers. In the symbol listing, main.o has an undefined reference to add(int, int), while math.o defines it. The linker matches those symbols.

Trigger both classes of error

Compiler error

Change the call to add("20", 22). Compilation fails because the argument types do not match the declaration. No object file is produced.

Linker error

Restore the call, compile both files, then link only main.o:

clang++ main.o -o app

The source was valid, so compilation succeeded. Linking fails with an undefined-symbol message because no linked object defines add.

Diagnostic rule: syntax, type and declaration problems are compiler errors. “Undefined reference/symbol,” “duplicate symbol,” and missing-library messages are linker errors.

Express the same build in CMake

add_executable(app
    main.cpp
    math.cpp
)
target_compile_features(app PRIVATE cxx_std_20)

CMake still performs the same separate compilations and final link; it simply generates and schedules the commands.

Completion checklist

  • Two source files produce two object files.
  • You linked the object files into a working executable.
  • You inspected one preprocessed file and symbol table.
  • You can distinguish a compiler error from a linker error.
  • You can explain declarations, definitions and unresolved symbols.

Step 7 of 200 · Modern C++

Learn header/source separation

Create a small library with a public header and private implementation, then understand include guards, declarations, definitions and dependency boundaries.

Definition of done: your program consumes a function through a header, compiles its implementation separately, links successfully, and remains correct when the header is included twice.

Give each file one job

  • A header (.hpp) publishes declarations: the names and types other translation units may use.
  • A source file (.cpp) owns definitions: the executable implementation.
  • A consuming source includes the header instead of manually repeating declarations.

Why separate them? Consumers compile against a stable interface while implementation details can change independently. It also prevents declarations from silently drifting apart.

Create a greeting library

include/roadmap/greeting.hpp:

#pragma once

#include <string>
#include <string_view>

namespace roadmap {
std::string make_greeting(std::string_view name);
}

src/greeting.cpp:

#include "roadmap/greeting.hpp"

namespace roadmap {
std::string make_greeting(std::string_view name) {
    return "Hello, " + std::string{name} + "!";
}
}

apps/hello/main.cpp:

#include "roadmap/greeting.hpp"
#include "roadmap/greeting.hpp"  // intentional duplicate test

#include <iostream>

int main() {
    std::cout << roadmap::make_greeting("backend engineer") << '\n';
}

#pragma once makes the header’s declarations appear once per translation unit even if include paths reach it multiple times. A portable traditional guard is:

#ifndef ROADMAP_GREETING_HPP
#define ROADMAP_GREETING_HPP
// declarations
#endif

Build a real library target

add_library(roadmap_core
    src/greeting.cpp
)

target_include_directories(roadmap_core
    PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include
)
target_compile_features(roadmap_core PUBLIC cxx_std_20)

add_executable(hello_backend apps/hello/main.cpp)
target_link_libraries(hello_backend PRIVATE roadmap_core)

PUBLIC on the include directory means the library and its consumers need that path. PRIVATE linking means hello_backend uses the library but does not promise to re-export it.

Rules that prevent subtle bugs

  • Include the matching header first in its .cpp file. This proves the header declares everything the implementation needs.
  • Headers must be self-contained: including one in an otherwise empty source file should compile.
  • Do not put ordinary non-inline function definitions or global-variable definitions in headers; every includer would create another definition.
  • Use forward declarations only when a complete type is not required. Prefer clarity over aggressively reducing includes.
  • Never write using namespace ... in a header; it pollutes every file that includes it.

Run the failure experiments

  1. Remove src/greeting.cpp from add_library. The final link should fail with an undefined symbol.
  2. Remove #pragma once and define the same class twice by including the header twice. Compilation should report redefinition.
  3. Change the header parameter to int without changing the source definition. You now have different functions; compilation or linking exposes the mismatch.

Completion checklist

  • The public header is self-contained and protected against repeated inclusion.
  • The source includes its own matching header first.
  • CMake builds a library target and links the executable to it.
  • You can explain declaration vs definition.
  • You reproduced an undefined-symbol failure by omitting the implementation.

Step 8 of 200 · Modern C++

Learn namespaces

Organize names into intentional domains, avoid collisions between libraries, and learn the few namespace habits that keep headers safe.

Definition of done: you can define and call names in nested namespaces, use aliases locally, explain qualified lookup, and avoid namespace pollution in public headers.

The collision namespaces solve

Large programs combine standard-library names, third-party libraries and your own modules. Two unrelated components may both define Config, connect or Logger. A namespace adds a logical scope without creating an object.

namespace roadmap::network {
struct Endpoint {
    std::string host;
    int port;
};

void connect(const Endpoint& endpoint);
}

namespace roadmap::database {
void connect(std::string_view connection_string);
}

The fully qualified names are roadmap::network::connect and roadmap::database::connect. They coexist because they occupy different namespaces.

Build and call names deliberately

#include <iostream>
#include <string>
#include <string_view>

namespace roadmap::network {
struct Endpoint { std::string host; int port; };

void connect(const Endpoint& endpoint) {
    std::cout << "TCP " << endpoint.host << ':' << endpoint.port << '\n';
}
}

namespace roadmap::database {
void connect(std::string_view url) {
    std::cout << "DB " << url << '\n';
}
}

int main() {
    roadmap::network::Endpoint api{"127.0.0.1", 8080};
    roadmap::network::connect(api);
    roadmap::database::connect("postgres://localhost/roadmap");
}

The :: scope-resolution operator asks for a name within a scope. Starting with ::roadmap requests lookup from the global namespace, which can disambiguate a shadowed name.

Use aliases and using-declarations narrowly

int main() {
    namespace net = roadmap::network;
    using roadmap::database::connect;

    net::Endpoint api{"localhost", 8080};
    net::connect(api);
    connect("postgres://localhost/roadmap");
}

A namespace alias shortens a long path while preserving where names come from. A using-declaration imports one name. By contrast, using namespace roadmap::network; imports every eligible name and makes collisions more likely.

Never put a using-directive in a header. Every translation unit that includes the header would inherit it, including code you do not control. Fully qualify names in public interfaces.

Understand anonymous namespaces

Implementation-only helpers in a .cpp file can use an unnamed namespace:

namespace {
constexpr int default_port = 8080;

bool is_valid_port(int port) {
    return port > 0 && port <= 65535;
}
}

These names have internal linkage: other translation units cannot refer to them. This is useful for private file-level helpers, not public header APIs.

Choose meaningful boundaries

  • Use a stable project namespace such as roadmap.
  • Add subnamespaces for real domains such as network, http and storage.
  • Avoid mirroring every folder mechanically if it makes names excessively long.
  • Do not add declarations to std except the few customizations the standard explicitly permits.

Completion checklist

  • Two same-named functions coexist in different namespaces.
  • You can call both with qualified names.
  • You used a namespace alias inside one function.
  • You can explain using-declaration vs using-directive.
  • Your public header contains no using-directive.

Step 9 of 200 · Modern C++

Learn stack vs heap

Understand automatic and dynamic storage, observe when objects are created and destroyed, and stop treating “stack” and “heap” as vague performance labels.

Definition of done: you can classify common object lifetimes, observe scope-driven destruction, allocate dynamic storage safely with RAII, and explain why returning a pointer to a local object is invalid.

Start with storage duration

“Stack” and “heap” are implementation-oriented terms. The C++ rules are expressed as storage duration:

  • Automatic: a local object normally exists until its block ends.
  • Dynamic: storage obtained with allocation exists until explicitly released or its owning RAII object releases it.
  • Static: the object lives for the program’s duration.
  • Thread: one instance lives for each thread.

Observe automatic lifetime

#include <iostream>
#include <string>
#include <utility>

struct Trace {
    std::string name;
    explicit Trace(std::string value) : name{std::move(value)} {
        std::cout << "construct " << name << '\n';
    }
    ~Trace() { std::cout << "destroy " << name << '\n'; }
};

int main() {
    Trace outer{"outer"};
    {
        Trace inner{"inner"};
        std::cout << "inside block\n";
    }
    std::cout << "after block\n";
}

inner is destroyed at the closing brace; outer is destroyed when main ends. Destruction runs in reverse construction order. This deterministic behavior is the basis of RAII.

Use dynamic storage safely

#include <memory>

int main() {
    auto item = std::make_unique<Trace>("dynamic");
    item->name = "owned dynamically";
} // unique_ptr releases the object here

The Trace object uses dynamic storage, but the local unique_ptr owns it. No manual delete is required. Prefer values first, then smart pointers when an object truly needs independent or polymorphic lifetime.

Inspect addresses without over-interpreting them

int local = 7;
auto dynamic = std::make_unique<int>(9);

std::cout << "local:   " << &local << '\n';
std::cout << "dynamic: " << dynamic.get() << '\n';

The addresses will often lie in visibly different ranges, but the C++ standard does not prescribe a particular stack direction or allocator layout. Use the experiment to see distinct storage, not to infer portable address rules.

Recognize a dangling pointer

int* broken() {
    int local = 42;
    return &local; // wrong: local dies at function exit
}

After the function returns, the pointer still contains an address but no live int exists there. Dereferencing it is undefined behavior. Return the value instead:

int correct() {
    return 42;
}
Key idea: a pointer value does not keep an object alive. Lifetime and ownership must be established separately.

Choose storage based on semantics

  • Use local values for ordinary scoped work.
  • Use containers such as std::vector for variable-sized collections; they manage their own dynamic storage.
  • Use std::unique_ptr when one owner needs dynamic lifetime.
  • Avoid raw new and delete in application code.
  • Do not put huge arrays on the stack; stack space is limited.

Completion checklist

  • You observed reverse-order destruction at scope exit.
  • You allocated an object through make_unique.
  • You can explain automatic, dynamic and static storage duration.
  • You can identify why returning a local address is invalid.
  • You choose values by default and dynamic ownership only for a reason.

Step 10 of 200 · Modern C++

Learn pointers

Use pointers as explicit, nullable references to existing objects; practice dereferencing and member access; and learn the lifetime rules that make pointer code safe or dangerous.

Definition of done: you can create, inspect, dereference and null-check pointers, pass an optional object to a function, traverse contiguous data, and identify dangling pointers.

A pointer stores an address

int port = 8080;
int* pointer = &port;

std::cout << port << '\n';       // value: 8080
std::cout << &port << '\n';      // address of port
std::cout << pointer << '\n';    // same address
std::cout << *pointer << '\n';   // value at that address

*pointer = 9090;                    // modifies port

&port takes an address. *pointer dereferences it. The pointer’s type records what kind of object is expected at the address, which determines type checking and pointer arithmetic.

Represent “no object” with nullptr

struct Request {
    int status_code;
};

void print_status(const Request* request) {
    if (request == nullptr) {
        std::cout << "no request\n";
        return;
    }
    std::cout << request->status_code << '\n';
}

int main() {
    Request request{200};
    print_status(&request);
    print_status(nullptr);
}

request->status_code is shorthand for (*request).status_code. Null must be checked before dereferencing. Prefer nullptr over 0 or NULL because it has a dedicated pointer-compatible type.

API signal: use a pointer parameter when “no object” is a meaningful input. If the object is required, a reference usually communicates that contract better.

Read const placement

int value = 10;
int other = 20;

const int* view = &value;      // pointer to const int
int* const fixed = &value;     // const pointer to mutable int
const int* const both = &value;
  • view may point elsewhere, but cannot modify the pointed-to int.
  • fixed cannot point elsewhere, but can modify value.
  • both can do neither.

Traverse contiguous data

int values[]{10, 20, 30, 40};
int* begin = values;
int* end = values + 4;

for (int* current = begin; current != end; ++current) {
    std::cout << *current << '\n';
}

Adding one advances by one int, not one byte. Arithmetic is only valid within the same array (or one-past its end), and the one-past pointer must not be dereferenced. In ordinary code, prefer a range-for loop, iterators or std::span; this exercise explains what those abstractions build on.

Separate pointer from ownership

A raw pointer normally observes an object; it does not say who owns or destroys it.

int* dangling = nullptr;
{
    int temporary = 42;
    dangling = &temporary;
}
// *dangling is now undefined behavior

Also avoid uninitialized pointers:

int* bad;             // indeterminate address
int* safe = nullptr;  // explicitly points to nothing
Do not “test” undefined behavior for correctness. A dangling dereference may appear to work and still be invalid. Sanitizers help catch mistakes: compile Clang/GCC examples with -fsanitize=address,undefined -fno-omit-frame-pointer.

Completion checklist

  • You can explain &, * and ->.
  • You null-check before dereferencing optional pointers.
  • You can read pointer-to-const and const-pointer declarations.
  • You traversed an array without moving outside its bounds.
  • You can identify uninitialized, null and dangling pointers.

Step 11 of 200 · Modern C++

Learn references

Use references to express required aliases, pass objects without copying, return access to existing state safely, and understand where references differ from pointers.

Definition of done: you can choose value, const&, mutable &, or pointer parameters based on intent, and you never return a reference to a dead local object.

A reference is an alias

int port = 8080;
int& alias = port;

alias = 9090;
std::cout << port << '\n'; // 9090

An lvalue reference must bind when declared and normally cannot be reseated. Assigning to alias assigns to port; it does not make the reference refer to a new integer.

Make parameter intent visible

struct Request {
    std::string path;
    int retry_count{};
};

void print_request(const Request& request) { // required, read-only, no copy
    std::cout << request.path << '\n';
}

void schedule_retry(Request& request) {      // required and modified
    ++request.retry_count;
}

void maybe_print(const Request* request) {   // optional
    if (request) print_request(*request);
}

A useful first decision table:

  • Small independent input: pass by value, such as int.
  • Large or non-copying read-only input: pass by const T&.
  • Required output/in-out object: pass by T&.
  • Optional non-owning object: pass by const T* or T*.

Return references only to live objects

class ServerConfig {
public:
    const std::string& host() const { return host_; }
    std::string& host() { return host_; }

private:
    std::string host_{"localhost"};
};

These references remain valid while the ServerConfig object and its host_ member remain alive and unmoved. A reference-returning API exposes the original object, not a copy.

const std::string& broken() {
    std::string local{"gone soon"};
    return local; // wrong: dangling reference
}
Lifetime rule: returning by reference does not extend the lifetime of a local variable. Return a value; modern C++ efficiently elides or moves it.

Store aliases explicitly when necessary

References themselves are not regular reseatable objects and cannot be elements of a standard container. std::reference_wrapper provides an object-like, reseatable reference:

#include <functional>
#include <vector>

int first = 1;
int second = 2;
std::vector<std::reference_wrapper<int>> values{first, second};

for (int& value : values) {
    value *= 10;
}

Prove copies and aliases differ

Request original{"/health"};
Request copy = original;
Request& reference = original;

copy.path = "/copy";
reference.path = "/live";

std::cout << original.path << '\n'; // /live

The copy owns independent state; the reference names the original. This distinction becomes central in APIs, loops and ownership design.

Completion checklist

  • You modified an object through a reference.
  • You chose parameter forms based on required/optional and read/write intent.
  • You can explain why a local reference return dangles.
  • You know a returned member reference depends on the owning object’s lifetime.
  • You compared copy behavior with alias behavior.

Step 12 of 200 · Modern C++

Learn const

Make immutability part of the type system, design const-correct functions and classes, and understand how const behaves with values, references and pointers.

Definition of done: you use const by default for unchanged values, write const-correct member functions, and can read all common const/pointer combinations.

Const is a compile-time contract

const int default_port = 8080;
// default_port = 9090; // compiler error

int runtime_port = read_port();
const int selected_port = runtime_port;

const means the program cannot modify an object through that name after initialization. Unlike constexpr, a const value does not have to be known at compile time.

Why const by default? It narrows possible state changes, documents intent to readers, and lets the compiler reject accidental mutation.

Use const references for read-only access

struct Request {
    std::string method;
    std::string path;
};

void log_request(const Request& request) {
    std::cout << request.method << ' ' << request.path << '\n';
}

The reference avoids a copy. Its const qualifier prevents log_request from modifying the request. It also allows both const and non-const arguments to bind.

Make member functions const-correct

class Connection {
public:
    explicit Connection(int id) : id_{id} {}

    int id() const { return id_; }
    bool is_open() const { return open_; }
    void close() { open_ = false; }

private:
    int id_;
    bool open_{true};
};

void inspect(const Connection& connection) {
    std::cout << connection.id() << '\n';
    // connection.close(); // rejected: close is not const
}

The trailing const applies to the implicit this object. It promises not to modify ordinary data members and makes the method callable on a const object.

Provide const and mutable access

class Headers {
public:
    std::string& at(std::size_t index) { return values_.at(index); }
    const std::string& at(std::size_t index) const { return values_.at(index); }

private:
    std::vector<std::string> values_;
};

Overloading on member-function constness preserves the caller’s permissions: mutable objects get mutable access; const objects get read-only access.

Read const from right to left

int first = 1;
int second = 2;

const int* pointer_to_const = &first;
pointer_to_const = &second;        // allowed
// *pointer_to_const = 3;          // rejected

int* const const_pointer = &first;
*const_pointer = 3;                // allowed
// const_pointer = &second;        // rejected

const int* const fixed_view = &first;

A practical reading method is to start at the variable name and move outward. const_pointer is const, then it is a pointer, then it points to int.

Know the narrow mutable exception

class Metrics {
public:
    int requests() const {
        ++read_count_;
        return requests_;
    }
private:
    int requests_{};
    mutable int read_count_{};
};

mutable permits internal bookkeeping that does not change the object’s logical value. Use it sparingly—for caches, mutexes or diagnostics—not to bypass a poor const design.

Avoid const_cast. Removing constness and modifying an object originally defined as const is undefined behavior. Fix the API instead of silencing its contract.

Completion checklist

  • Unchanged local variables are declared const.
  • Read-only large parameters use const T&.
  • Observer member functions have trailing const.
  • You can interpret pointer-to-const and const-pointer.
  • You can explain const vs constexpr and physical vs logical constness.

Step 13 of 200 · Modern C++

Learn object lifetime

Track exactly when objects begin and end their lifetime, recognize dangling views and references, and design APIs whose returned data remains valid long enough.

Definition of done: you can annotate the lifetime of every object and view in a short program, identify three dangling cases, and repair them by changing ownership or return types.

Lifetime is not just allocated bytes

An object’s lifetime begins after suitable storage exists and initialization completes. It ends when destruction starts or when its storage is reused or released. Storage may still contain old-looking bits after lifetime ends, but accessing them as the dead object is invalid.

struct Session {
    explicit Session(int id) : id{id} { std::cout << "start\n"; }
    ~Session() { std::cout << "end\n"; }
    int id;
};

int main() {
    Session session{7}; // lifetime begins after initialization
    std::cout << session.id << '\n';
} // destructor runs; lifetime ends

Observe temporary lifetime

std::string make_name() { return "roadmap"; }

const std::string& extended = make_name();
std::cout << extended << '\n';

Binding a temporary directly to this local const reference extends its lifetime to the reference’s scope. Do not generalize this to every reference hop; returning a reference parameter or storing a view does not automatically extend the original object.

Treat views as borrowed access

std::string_view broken_name() {
    std::string local{"backend"};
    return local; // dangling string_view
}

std::string correct_name() {
    return "backend"; // caller owns the returned value
}

std::string_view owns no characters. The local string dies at function exit, leaving the view dangling. Views are powerful only when the referenced data clearly outlives them.

Learn iterator and reference invalidation

std::vector<int> values{1, 2, 3};
int& first = values.front();

values.push_back(4); // may reallocate
// using first may now be invalid

If capacity was exhausted, push_back moves elements to new storage, invalidating pointers, references and iterators into the old storage. Consult each container operation’s invalidation rules; they differ by container and operation.

Watch captures used later

std::function<void()> make_callback() {
    std::string message{"ready"};
    return [&message] { std::cout << message; }; // dangling capture
}

std::function<void()> safe_callback() {
    std::string message{"ready"};
    return [message = std::move(message)] { std::cout << message; };
}

Asynchronous backends make this mistake especially dangerous: a callback often runs after the creating function has returned. Capture required state by value or give it explicit shared ownership.

Use tools, but reason first

clang++ -std=c++20 -g -fsanitize=address,undefined \
  -fno-omit-frame-pointer lifetime.cpp -o lifetime
./lifetime

Sanitizers can catch many use-after-free and bounds problems. They cannot prove that every borrowed view is safe, so document and reason about the owner and the required lifetime.

Lifetime audit: for each pointer, reference, iterator, span, string view or callback capture, ask “who owns the object, and can that owner end or move it before this use?”

Completion checklist

  • You can state where each local object’s lifetime begins and ends.
  • You repaired a function returning a dangling string view.
  • You understand vector reallocation invalidation.
  • You repaired a callback that captured a local by reference.
  • You ran an example under AddressSanitizer.

Step 14 of 200 · Modern C++

Learn RAII

Tie resource ownership to object lifetime so files, locks, sockets and memory are released on every path—including early returns and exceptions.

Definition of done: you can wrap a C resource in a move-only RAII class, prove cleanup happens on multiple control-flow paths, and prefer existing standard RAII types when available.

Resource acquisition is initialization

RAII means a constructor establishes an invariant by acquiring or accepting a resource, and the destructor releases it. The resource-owning object lives in an ordinary scope, so C++ automatically runs cleanup when that scope ends.

Resources include memory, file handles, sockets, mutex locks, database transactions and temporary files—not just objects created with new.

First use an existing RAII type

#include <fstream>
#include <stdexcept>
#include <string>

std::string read_first_line(const std::string& path) {
    std::ifstream input{path};
    if (!input) {
        throw std::runtime_error{"cannot open " + path};
    }

    std::string line;
    std::getline(input, line);
    return line;
} // input closes the file here, even during stack unwinding

std::ifstream owns its file handle. There is no separate close call to forget. Standard types such as vector, string, unique_ptr, lock_guard and file streams already embody RAII.

Write a move-only FILE wrapper

#include <cstdio>
#include <stdexcept>
#include <utility>

class File {
public:
    File(const char* path, const char* mode) : handle_{std::fopen(path, mode)} {
        if (!handle_) throw std::runtime_error{"fopen failed"};
    }

    ~File() {
        if (handle_) std::fclose(handle_);
    }

    File(const File&) = delete;
    File& operator=(const File&) = delete;

    File(File&& other) noexcept
        : handle_{std::exchange(other.handle_, nullptr)} {}

    File& operator=(File&& other) noexcept {
        if (this != &other) {
            if (handle_) std::fclose(handle_);
            handle_ = std::exchange(other.handle_, nullptr);
        }
        return *this;
    }

    std::FILE* get() const noexcept { return handle_; }

private:
    std::FILE* handle_{};
};

Copying is disabled because two owners would both close the same handle. Moving transfers the handle and clears the old owner. noexcept makes the transfer safe for standard containers and cleanup paths.

Prove cleanup on every path

void write_status(bool fail) {
    File output{"status.txt", "w"};
    std::fputs("starting\n", output.get());

    if (fail) {
        throw std::runtime_error{"simulated failure"};
    }

    std::fputs("complete\n", output.get());
}

Call it once with false and once with true inside a try/catch. In both cases the destructor closes the handle. This works because stack unwinding destroys fully constructed local objects.

See RAII in concurrency

std::mutex mutex;
int request_count = 0;

void record_request() {
    std::lock_guard lock{mutex};
    ++request_count;
} // unlocks automatically

Manual lock()/unlock() fails when an early return or exception skips the unlock. The guard makes the lock lifetime visible and mechanically correct.

RAII design test: after successful construction, the object is usable; after destruction, the resource is released; partial construction failure leaks nothing; ownership transfer is explicit.

Completion checklist

  • You can explain why deterministic destruction enables RAII.
  • You used a standard RAII file stream.
  • Your custom wrapper releases its handle exactly once.
  • The wrapper cannot be copied and can be moved.
  • Cleanup works during normal return and exception unwinding.
  • You can name the RAII types for memory, files and locks.

Step 15 of 200 · Modern C++

Learn constructors and destructors

Design a class that is valid from the moment it exists, understand initialization order, choose explicit constructors, and observe deterministic destruction.

Definition of done: you can enforce a class invariant in its constructor, use a member-initializer list, explain actual initialization and destruction order, and prevent unintended implicit conversions.

Constructors establish invariants

An invariant is a condition that every usable object must satisfy. For a listening endpoint, the host must be non-empty and the port must be in 1..65535. Reject invalid state at construction instead of forcing every method to recheck it.

#include <stdexcept>
#include <string>
#include <utility>

class Endpoint {
public:
    Endpoint(std::string host, int port)
        : host_{std::move(host)}, port_{port} {
        if (host_.empty()) {
            throw std::invalid_argument{"host cannot be empty"};
        }
        if (port_ < 1 || port_ > 65535) {
            throw std::out_of_range{"port must be 1..65535"};
        }
    }

    const std::string& host() const noexcept { return host_; }
    int port() const noexcept { return port_; }

private:
    std::string host_;
    int port_;
};

The member-initializer list initializes members directly. Assigning inside the constructor body would first default-initialize members and then replace their values.

Know the real initialization order

class Server {
public:
    Server(int port, std::string name)
        : name_{std::move(name)}, port_{port} {}

private:
    int port_;
    std::string name_;
};

Despite the initializer-list order, port_ initializes first because members initialize in declaration order. Base classes initialize before members. Destruction happens in reverse order. Keep the initializer list in declaration order so the code communicates reality and avoids dependency bugs.

Block accidental conversions

class Timeout {
public:
    explicit Timeout(int milliseconds) : milliseconds_{milliseconds} {}
private:
    int milliseconds_;
};

void set_timeout(Timeout timeout);

set_timeout(Timeout{500}); // clear
// set_timeout(500);       // rejected because constructor is explicit

A single-argument constructor can otherwise become an implicit conversion. Use explicit unless conversion is truly part of the type’s intended meaning.

Delegate instead of duplicating

class RetryPolicy {
public:
    RetryPolicy() : RetryPolicy{3, 100} {}

    RetryPolicy(int attempts, int delay_ms)
        : attempts_{attempts}, delay_ms_{delay_ms} {
        if (attempts_ < 0 || delay_ms_ < 0) {
            throw std::invalid_argument{"negative retry setting"};
        }
    }

private:
    int attempts_;
    int delay_ms_;
};

The default constructor delegates to the validating constructor, leaving one place that establishes the invariant.

Observe construction and destruction

#include <iostream>
#include <string>
#include <utility>

struct Trace {
    std::string name;
    explicit Trace(std::string n) : name{std::move(n)} {
        std::cout << "+ " << name << '\n';
    }
    ~Trace() {
        std::cout << "- " << name << '\n';
    }
};

int main() {
    Trace first{"first"};
    Trace second{"second"};
}

The output destroys second before first. Destructors should release owned resources and should not throw; throwing during exception unwinding can terminate the program.

Prefer the Rule of Zero

If all members manage themselves—std::string, vector, smart pointers and RAII wrappers—you usually write no destructor, copy constructor or move constructor. The compiler-generated operations compose the members correctly. Write special member functions only when the class directly manages a resource or needs unusual semantics.

Experiment: try constructing Endpoint{"", 8080} and Endpoint{"localhost", 70000} inside try/catch. Confirm no invalid Endpoint becomes usable.

Completion checklist

  • Your constructor establishes and validates an invariant.
  • Members are initialized through a member-initializer list.
  • The initializer list follows declaration order.
  • A single-argument constructor is explicit.
  • Shared validation uses a delegating constructor.
  • You can explain reverse destruction order and the Rule of Zero.
